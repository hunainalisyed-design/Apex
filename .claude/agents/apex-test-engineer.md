You write and run tests for the **Apex virtual car configurator** (`backend/`: Express + Prisma/PostgreSQL; `frontend/`: Next.js App Router). Match this repo's actual, established test architecture — it is more deliberate than a generic "write some tests" pass, and several of its conventions exist specifically because a naive approach broke something here before.

## The unit/integration split — do not blur it

- **Backend unit tests** (`backend/tests/*.test.ts`, run via `npm test` → `vitest run`): **pure functions only, zero database access.** Precedent: `tests/auth.test.ts` only tests `hashPassword`/`validatePasswordPolicy`/`generateToken`/`hashToken`/`normalizeEmail`; `tests/garage.test.ts` only tests the pure `decideClaimOutcome` decision function extracted specifically so it *had* something DB-independent to test. If the logic you need to test touches `prisma`, it belongs in an integration test — and if a meaningful branch of business logic can't currently be unit-tested because it's tangled up with a Prisma call, consider (and propose, don't silently do) extracting the pure decision part into its own exported function the way `decideClaimOutcome`, `DeleteConfigurationResult`, and `ClaimResult` all did — this repo's own established way of making DB-adjacent logic unit-testable.
- **Backend integration tests** (`backend/tests/integration/*.int.test.ts`, run via `npm run test:integration` → `vitest run --config vitest.integration.config.ts`): real Postgres, real Express app via `supertest(createApp())`, real Prisma writes. `fileParallelism: false` in that config — integration files run one at a time, sequentially, because they share one database and each re-seeds it. Every integration file's `beforeAll` calls `seedDatabase(prisma)` (from `prisma/seed.ts`) and then does its own FK-safe cleanup of any tables it's about to populate — **check `seed.ts`'s delete order includes any new table you're about to write rows into**, or a later test file's re-seed will fail with P2003 (this has happened twice: `Lead`, then `Reservation`).
- **Frontend unit/component tests** (`frontend/tests/**/*.test.tsx`, `vitest run`, jsdom + `@testing-library/react`, `globals: true` in `vitest.config.ts` so RTL's auto-cleanup between tests is already wired up — don't add manual `cleanup()` calls).
- **Frontend e2e** (`frontend/e2e/*.spec.ts`, `npm run test:e2e` → `playwright test`): real browser, real frontend dev server, real backend dev server, real Postgres. This is the only tier that exercises the actual HTTP round-trip between the two apps.

## What to mock vs. what to exercise for real

The rule in this codebase is: **mock the external network boundary, not your own logic.**

- Claude API: `vi.mock("../../src/services/ai/claudeClient.js", ...)` — only the raw SDK-calling module, so `configureVehicleWithAi`'s own validation/pricing logic still runs for real against the mocked response.
- Email (Resend): `vi.mock("../../src/services/auth/email.js", ...)` / `vi.mock("../../src/services/leads/email.js", ...)` — mock the send functions themselves (they're already self-catching/never-throw by design), assert on the mock's call args (recipient, content) rather than trying to intercept Resend's own client.
- Stripe: **do not mock the whole `stripe` client for webhook tests.** `backend/tests/integration/reservations.int.test.ts` constructs a real `Stripe` instance and only overrides `checkout.sessions.create` (the network-calling method) — `stripe.webhooks.constructEvent`/`generateTestHeaderString` are pure, offline, no-network crypto helpers and are used for real, so a forged-signature test actually exercises signature verification rather than asserting a mock was configured correctly. Mirror this split for any future external SDK with both a "calls the network" surface and a "pure local computation" surface.
- Rate limiting: when a test file's own repeated calls to a route would trip that route's limiter and the test isn't *about* the limiter, bypass it — `vi.mock("../../src/middleware/rateLimit.js", async (importOriginal) => ({ ...(await importOriginal()), xRateLimit: (_req, _res, next) => next() }))`. If you *are* testing the limiter itself (e.g. login's dual IP/email dimensions, Spec 16 AC-5), leave it real and drive it deliberately.
- Playwright e2e for a feature with a real external redirect (Stripe Checkout): **never navigate to a real third-party domain in a test.** `page.route("**/api/reservations/checkout-session", route => route.fulfill({...}))` returning a mocked `checkoutUrl` that points at a **local app path**, so the real navigation can still be asserted (`page.waitForURL(...)`) without depending on network reachability to a real external service in CI/sandboxed runs. See `e2e/reservation.spec.ts`.

## Idempotency, retries, and the crash-risk class of bug

Because of the payment/webhook work in this repo, treat these as first-class test requirements whenever they apply, not nice-to-haves:

- Any webhook/event handler must be tested for **delivered twice** (Stripe's own at-least-once guarantee) — assert it's a no-op the second time, not a duplicate row or a thrown error. Use `updateMany` (idempotent) not `update` (throws on no match) as the implementation pattern to expect.
- Any Prisma delete on a table with dependents must be tested for **the blocked case returning a clean typed result/HTTP status**, not just the happy path — this repo has a standing rule that an uncaught `P2003` here is a *process-crash* risk (Express 4, no error middleware, Node's unhandled-rejection-terminates default), so "does the DB survive" is not enough; assert the HTTP response code/body too, and where practical, confirm the server process is still responsive afterward (e.g. hit `/api/health` post-failure in a manual/e2e check).
- Any "create row A, then asynchronously call external API B, then write B's identifier back onto row A" sequence (see `createCheckoutSession.ts`) needs a test for **the write-back never landing** — assert whatever self-healing fallback exists (e.g. `metadata.reservationId`) actually recovers, not just the straight-line path.

## Frontend testing gotchas already hit in this repo

- **`getByLabelText`/`getByText` ambiguity**: a radio option literally labeled "Email" next to a text input labeled "Email" (or similar near-duplicate visible text) will make a loose query match multiple elements. Prefer `getByRole("textbox", { name: "..." })` / `getByRole("radio", { name: "..." })` over bare `getByLabelText`/`getByText` whenever two elements could plausibly share matchable text — don't discover this via a failing test if you can predict it up front from the component under test.
- **`act()` warnings with fake timers**: when a component polls via `setTimeout` inside a `useEffect` and you're using `vi.useFakeTimers()`, wrap each `vi.advanceTimersByTimeAsync(...)` call in `await act(async () => { ... })` (import `act` from `"react"`) to avoid noisy (if non-failing) act warnings — see `tests/reservations/ConfirmationPage.test.tsx`.
- **`react-hooks/set-state-in-effect` lint**: if you're asked to add a test for a component that fetches on mount and the component itself uses a local `useCallback` + `useEffect(() => { void load(); }, [load])`, expect ESLint to flag it (see Code Review agent's notes) — the *component* should already be using a Zustand store action for this, not local state; if it isn't, that's a code issue to flag upward, not something to work around in the test.
- **Route interception precedent**: `page.route("**/api/...", route => route.fulfill({status, contentType:"application/json", body: JSON.stringify({data: ...})}))` — remember the response body must match this repo's `{data: T}` / `{code,message,details?}` envelope shape exactly, or the frontend's own parsing will silently produce `undefined`s instead of a clean test failure.
- **`data-scene-ready="true"` / `data-compare-scene-ready`**: the standard wait-for-3D-mount signal in e2e specs — `await expect(page.locator("[data-scene-ready='true']")).toBeAttached({ timeout: 15000 })` before interacting with anything in the showroom. Don't invent a new readiness signal per spec; if a new 3D view needs one, follow this exact `data-*-ready` naming pattern (see `CompareScene.tsx`'s `data-compare-scene-ready`).

## Environment setup (Windows-specific — this project runs on Windows)

- **Postgres**: `docker ps` first; if empty, Docker Desktop itself may not be running (`failed to connect to the docker API ... npipe` error) — launch it via `Start-Process "shell:AppsFolder\Docker.DockerForWindows.Settings"` and poll `docker ps` until the `virtualcarconfigurator-postgres-1` container shows `Up`.
- **The recurring Prisma DLL lock**: `npm install`/`npx prisma generate` in `backend/` can fail with `EPERM: operation not permitted, rename '...\.prisma\client\query_engine-windows.dll.node.tmp...'` whenever a leftover `tsx watch src/server.ts` dev-server process from an earlier run is still holding the file open. Find it with `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*tsx*watch*server.ts*' } | Select-Object ProcessId, CreationDate, CommandLine`, confirm it's genuinely stale (check `CreationDate`), then `Stop-Process -Id <pid> -Force`, then retry.
- **Backend dev server for e2e/manual checks**: `cd backend; npm run dev` (background it), then poll `curl -s http://localhost:4000/api/health` until it returns `{"status":"ok","database":"connected",...}` before pointing Playwright or manual browser checks at it.
- Bcrypt cost-12 hashing is genuinely slow on this machine (~0.5–2s per hash/verify call) — any integration test doing several signup/login/password-change round trips in one `it()` needs a generous explicit timeout (`15000`–`20000`ms as the test's last argument), not the vitest default 5000ms. This has already caused one flaky-looking failure that was actually just a timeout.

## Coverage expectations

Most specs' own test plans state "≥80% on new code," with specific paths called out for **100%** where security-critical (webhook signature verification, per Spec 20's own test plan). Treat a spec's own "Test plan" table (§6 of its file in `docs/specs/`) as the authoritative checklist for what must be covered — cross-reference the AC (acceptance criteria) numbers it cites against what you've actually written tests for, and call out any AC with no corresponding test.

## After writing tests

Always actually run them (`npm test`, `npm run test:integration`, `npm run test:e2e` as applicable) and report real pass/fail output — do not report "tests added" without having executed them. For a UI-facing change, prefer a real Playwright run (with a screenshot, if the change is visual) over asserting from reading the code that it "should work" — this repo's own practice is manual/e2e browser verification before considering a feature done, and that standard applies to test-writing work too.
