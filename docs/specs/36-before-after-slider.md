## 1. Problem statement

**Today:** A CarAI recommendation card (Spec 15) shows the proposed changes as a text list. SRS §35.4 wants a drag-to-compare visual slider between the current build and the AI-suggested one, making the difference immediately visible rather than requiring the user to read a list and imagine it.

**Who is affected:** Users evaluating a CarAI recommendation before deciding whether to apply it.

**Why it matters now:** It's a low-effort visual enhancement to an already-built feature (Spec 15), reusing Spec 11's capture mechanism rather than introducing anything new.

**Success looks like:** A recommendation card shows a slider; dragging it left reveals the current build, dragging right reveals what it would look like with CarAI's changes applied — before the user commits to anything.

---

## 2. Acceptance criteria

| # | Criterion |
|---|---|
| AC-1 | **Given** a CarAI recommendation card with a non-null recommendation (Spec 15, AC-5) **When** rendered **Then** it includes a before/after slider instead of (or alongside) the plain text list of changes |
| AC-2 | **Given** the slider **When** it needs a "before" and "after" image **Then** both are generated by briefly, invisibly applying each configuration state (current, then recommended) to an off-screen render pass using Spec 11's canonical-camera capture mechanism, then reverting the visible scene to the user's actual current state — the user's live 3D view is never disrupted while the comparison images are prepared |
| AC-3 | **Given** the two images **When** the slider renders **Then** dragging it (via mouse, touch, or keyboard arrow keys) moves a clip-path divider between them in real time, with no perceptible lag |
| AC-4 | **Given** the user decides to proceed **When** they click "Apply Configuration" (Spec 15, AC-7, unchanged) **Then** the actual apply behavior is identical to before this spec — the slider is a visualization aid only, not an alternate apply mechanism |
| AC-5 | **Given** `prefers-reduced-motion` **When** set **Then** the slider still functions (it's user-driven, not an ambient animation) but any transition/snap animation on the divider itself is removed |

## 5. UI states

| State | Behaviour |
|---|---|
| **Preparing images** | brief loading shimmer on the slider area while the two off-screen captures render (should be fast — same vehicle, just different materials) |
| **Ready** | interactive slider (AC-3) |
| **Error** | if either capture fails, falls back to Spec 15's original plain-text change list rather than showing a broken slider |

**Route(s):** integrated into Spec 15's `RecommendationCard`.
**Directory:** `frontend/src/components/ai/RecommendationCard/BeforeAfterSlider/`

## 6. Test plan

| Level | What it covers | Where |
|---|---|---|
| **Unit** | off-screen dual-capture sequencing correctly restores the live scene's actual state afterward | `frontend/tests/ai/beforeAfterCapture.test.ts` |

**Coverage:** ≥80% on new code.

---

## 7. Out of scope

- Any slider elsewhere in the app (e.g. comparing two saved builds) — scoped specifically to CarAI recommendations per SRS §35.4's own framing.

---

## 8. Risks and open questions

| # | Risk / question | Owner | Resolution |
|---|---|---|---|
| 1 | Briefly applying a hypothetical configuration to the live Three.js scene for capture, then reverting it, needs to be genuinely invisible to the user (no visible flash of the "after" state on the real 3D view). | Implementer | Open — recommend rendering the "after" state to an off-screen/hidden canvas rather than briefly mutating the visible one, avoiding any flash by construction rather than by timing. |
